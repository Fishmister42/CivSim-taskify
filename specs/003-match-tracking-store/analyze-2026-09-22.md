## What this pass looked for

The feature landed in one day, 46 tasks, and its `validation-results.md` is unusually honest
about what was and was not observed — the two obvious audit targets (a fabricated pass, a
success criterion with no evidence) are already handled there by name. So this pass went after
two other things:

1. **Requirements enforced by omission.** A store that never grew a `delete` method satisfies
   "MUST expose no operation that deletes" today and says nothing about tomorrow. This project
   has a name for the failure — a check written from the same mental model as the code — and a
   worked pattern for the fix (`tests/contract/test_read_only_boundary.py`).
2. **Surface that landed after the contract was written.** 003's files have been edited by other
   lanes since (`9f200d5`, the orphan-hygiene commit), and a published contract that no longer
   lists what the Protocol publishes is a contract its consumers cannot read.

Both produced findings. Requirement coverage was re-derived from the code and tests, not from
`tasks.md`'s claims.

### Correction to B6, recorded 2026-09-22 (T272) — B6 was rated on a stale premise

**B6 above is wrong in its diagnosis and therefore wrong in its severity. It is left in place
unedited, because a finding quietly rewritten is a finding nobody can audit; this is the
correction.**

B6 called the problem a **missing fixture** — "four of FR-018's eight named metrics are never
exercised ... add the four names to one existing fixture" — and rated it **LOW** on that basis.
It is a **missing producer**, which is a different defect and not a LOW one: a metric with no
producer can never be non-empty on real data no matter what any fixture asserts, so adding the
names to a fixture would have closed the finding while leaving the requirement just as
unsatisfiable as before. A test that demonstrates a name against a synthetic record is not
coverage of a series; it is coverage of a pass-through.

**Where the bad premise came from.** B6 repeated, as current fact, "all six yield series are
empty on every run this project has recorded, because 002's `compute_yields` is a no-op". That
claim was true until 2026-09-21 and false from then on: T258 landed
`catalogs/observations/yields.yaml`, `lua/ingame/yields.lua` and `src/civsim_harness/run/yields.py`,
and the production composition stopped using the `_no_yields` placeholder. The sentence survived
in `tests/unit/test_store_trends.py`'s docstring after the thing it described was fixed, and
**both** of 2026-09-22's audit reports read it back out of that file as though it were still
true. It has been corrected at the source.

**What the live store actually says (MEASURED 2026-09-22, read-only copy):**

| | Finding |
|---|---|
| Turn cycles with recorded yields | **77 of 93** — every one carrying all seven of `science`, `culture`, `gold`, `faith`, `tourism`, `gold_balance`, `faith_balance` |
| `city_count` / `unit_count` | **Produced and populated.** Derived per turn by `store/trends.py::turn_metrics_from` from the last observation's `cities.state` / `units.state` — never from `TurnCycle.yields`. All **93** last-step observations carry both lists. These two were **never missing**; B6 and the brief that followed it both treated them as unproduced |
| `production` / `food` | **The only genuine gap** — no producer, and no empire-level source to produce them from |

**Resolution.** FR-018 was amended for `production` and `food` alone, with the Principle I
reason recorded against the requirement itself in `spec.md` (Civilization VI shows both per city
and publishes no empire-wide figure for either, so an empire-level series would be a
harness-computed aggregate no human can read). `tourism` and the two balances were added to the
named set, since the harness has produced them since 2026-09-21 and the requirement did not say
so. The published set and the produced set are now both pinned as data —
`store/trends.py::FR018_METRIC_NAMES` against `run/yields.py::RECORDED_YIELD_METRICS` +
`DERIVED_METRICS` — and asserted equal in `tests/unit/test_yields.py`, so the next divergence is
a red test rather than an empty chart.

**Corrected rating**: B6 was **LOW / Coverage — "missing fixture"**. It should have been
**MEDIUM / Inconsistency — "requirement names four metrics, two of which have no producer"**.
The FR-018 row in the coverage table below (**PARTIAL — see B6**) reads correctly only with this
correction attached to it.

**The general lesson, since it cost two reports in one day**: a prose claim in a test docstring
is not evidence, and an analysis that repeats one without re-measuring inherits its expiry date.
B6's own measurement — grepping which names appear in fixtures — was sound; what it did not do
was check whether the *producer* existed, which one grep of `run/yields.py` would have answered.

**No CRITICAL finding.** No duplication, no ambiguity marker, no unresolved placeholder, and no
task without a mapped requirement.
